## User Scenarios & Testing

### User Story 1：客户自主解决酒店供应异常（Priority: P1）

作为已经登录的旅行平台客户，我希望在酒店查不到预订时，由系统主动识别关联订单、调查原因、提供可执行方案，并在我确认后完成处理和通知，使问题不需要内部客服参与也能闭环。

**Why this priority**：这是 V0.1 唯一必须端到端跑通的 Golden Journey，直接证明“自主客服闭环”成立。

**Independent Test**：使用合成客户 `C001` 发起“酒店查不到我的预订”，在其名下存在两笔未来酒店订单的前提下，验证系统能主动追问、安全定位目标订单、生成 180 元价差的改订方案、取得客户确认、完成一次改订、独立核验并通知客户；全程内部客服和运营人员介入次数为 0。

**Acceptance Scenarios**：

1. **Given** 已登录客户 `C001` 只说“酒店查不到我的预订”，现有信息无法唯一定位订单，**When** 系统处理该请求，**Then** 必须主动索取酒店名称和入住日期，不得展示任何候选订单详情。
2. **Given** `C001` 补充了酒店名称和入住日期，且 `C002` 存在相似订单，**When** 系统再次查找订单，**Then** 只能在 `C001` 的订单范围内唯一定位并验证目标订单归属，任何对话和处理记录均不得出现 `C002` 的订单内容。
3. **Given** 目标订单关联一条已知的酒店供应异常，且存在同日期、同等级、价差 180 元的替代酒店，**When** 系统调查问题并生成处理建议，**Then** 必须向客户说明有依据的异常原因、替代方案、入住日期和价差。
4. **Given** 当前方案按有效业务规则需要客户确认，**When** 客户尚未确认，**Then** 系统不得修改订单。
5. **Given** 客户明确确认当前版本的改订方案，**When** 系统执行改订，**Then** 目标订单只能发生一次符合确认内容的变更，重复消息或重复请求不得造成第二次变更。
6. **Given** 系统已经发起改订，**When** 判断业务是否处理成功，**Then** 必须重新读取实际订单结果，核对替代酒店、入住日期、订单状态和新确认号，不得只采信执行动作自身返回的成功信息。
7. **Given** 实际订单结果与客户确认的方案完全一致，**When** 系统通知客户处理结果，**Then** 必须说明改订后的关键订单信息，并将该问题标记为已解决。
8. **Given** 问题已经解决，**When** 本次服务结束，**Then** 必须生成结构化处理摘要，并保留足以复核订单定位、方案、确认、执行、核验和通知的完整记录。

### User Story 2：内部运营人员处理高风险方案（Priority: P2）

作为内部运营人员，我希望只在风险或时效条件要求人工介入时收到包含必要信息的处理请求，并只能对当前方案作出批准或拒绝，使高风险动作不会在缺少授权的情况下执行。

**Why this priority**：它证明自主闭环具有明确的人工介入边界；V0.1 只实现最小的 `APPROVE / REJECT` 能力，不扩展成人工客服工作台。

**Independent Test**：将替代酒店价差改为 800 元，验证系统识别为需要内部审批，在未取得审批时阻止订单变更，并允许运营人员对当前方案返回 `APPROVE` 或 `REJECT`。

**Acceptance Scenarios**：

1. **Given** 当前方案触发内部审批条件，**When** 系统完成风险判断，**Then** 必须向内部运营人员提供当前问题、方案、风险原因、处理时限和待决定事项。
2. **Given** 内部运营人员尚未作出决定，**When** 系统尝试推进订单变更，**Then** 必须拒绝执行并保持原订单不变。
3. **Given** 内部运营人员对当前版本方案作出 `APPROVE` 或 `REJECT`，**When** 系统接收该决定，**Then** 必须把决定与当前问题和方案绑定并留下记录。
4. **Given** 内部运营人员选择 `REJECT`，**When** 系统处理该决定，**Then** 不得执行被拒绝的方案，并必须停止该方案的自动推进。
5. **Given** 内部运营人员选择 `APPROVE`，**When** 系统记录该决定，**Then** V0.1 只需证明批准结果有效且可被后续步骤使用，不要求跑通高风险方案批准后的完整执行链路。

### User Story 3：补充信息并恢复未完成服务（Priority: P3）

作为暂时无法提供完整订单信息的客户，我希望系统明确告诉我还需要什么，并在等待超时后停止后台处理；如果我之后补充信息，系统应继续原来的问题，而不是让我重新开始。

**Why this priority**：它定义主动追问、等待和重新恢复的产品语义，避免系统无限等待、猜测订单或制造重复问题。

**Independent Test**：系统向 `C001` 成功发出补充信息请求后不再收到回复，验证 24 小时后该问题被标记为未完成并停止自动处理；随后由同一客户针对同一问题补充所需信息，验证系统恢复原问题和原有记录。

**Acceptance Scenarios**：

1. **Given** 系统已经成功发出补充信息请求，**When** 客户在 24 小时内提供有效信息，**Then** 系统必须继续原问题的订单定位流程。
2. **Given** 系统已经成功发出补充信息请求，**When** 24 小时内没有收到有效回复，**Then** 必须把该问题标记为未完成并停止后台自动处理。
3. **Given** 问题已因超时被标记为未完成，**When** 同一客户针对同一问题补充所需信息，**Then** 必须恢复原问题及其历史记录，不得创建重复问题。
4. **Given** 客户补充的信息仍不足以安全定位订单，**When** 系统重新判断信息完整性，**Then** 可以再次索取最小必要信息，不得猜测或选择某一候选订单。

### Edge Cases

- 多笔订单同时满足部分线索时，只能说明仍需哪些信息，不得暴露候选订单详情。
- 其他客户存在日期、酒店或姓名相似的订单时，该订单不得出现在当前客户可见内容或内部处理上下文中。
- 客户拒绝当前方案时，系统不得执行该方案，应继续提供可行替代方案或安全结束服务。
- 同一确认或执行请求被重复提交时，业务订单最多发生一次变更。
- 执行动作报告成功但实际订单没有更新时，系统必须判定处理未成功，不得通知客户已经解决。
- 实际订单已正确更新但客户通知临时失败时，系统不得重复执行订单变更，应继续尝试完成通知并保留失败记录。
- 结构化处理摘要生成失败时，不得回滚已经核验成功的业务结果，但本次 Demo 验收应判定为失败。
- 客户在问题标记为已解决后反馈仍未解决时，系统应恢复原问题和历史记录，不得创建重复问题。
- 客户回复时间与 24 小时截止时间接近时，应以客户消息实际到达时间判断是否在有效期内，而不是以程序处理先后顺序判断。

## Requirements

### Functional Requirements

- **FR-001**：系统必须从已登录会话获得可信客户身份，并把所有订单匹配和读取限制在该客户的数据范围内。
- **FR-002**：信息不足时，系统必须主动索取安全定位订单所需的最小信息，不得依靠猜测继续处理。
- **FR-003**：存在多个候选订单时，系统不得向客户或后续处理环节返回候选订单详情。
- **FR-004**：只有唯一定位订单且验证客户归属后，系统才能读取完整订单和关联异常信息。
- **FR-005**：系统必须基于已知订单事实、供应异常和业务规则生成问题诊断与处理方案，不得把推测表述为事实。
- **FR-006**：系统必须按照有效的业务规则判断方案所需的客户确认、内部审批或禁止执行条件，并记录所采用的规则版本和判断原因。
- **FR-007**：需要客户确认的方案在取得当前客户对当前版本方案的明确确认前不得执行。
- **FR-008**：需要内部审批的方案在取得有效审批前不得执行；V0.1 中运营人员的决定只允许为 `APPROVE` 或 `REJECT`。
- **FR-009**：重复的客户确认、审批或执行请求不得造成重复订单变更。
- **FR-010**：产生订单变更后，系统必须从实际业务结果中独立核验处理是否符合已确认方案，不得仅根据执行动作的返回值宣告成功。
- **FR-011**：实际业务结果与已确认方案不一致时，系统不得把问题标记为已解决，也不得向客户发送成功通知。
- **FR-012**：只有业务结果核验通过且客户通知成功后，系统才能把问题标记为已解决。
- **FR-013**：补充信息请求发出后 24 小时没有有效回复时，系统必须把问题标记为未完成并停止自动处理。
- **FR-014**：同一客户针对同一问题在关闭后补充信息或对处理结果提出异议时，系统必须恢复原问题及其历史记录，不得创建重复问题。
- **FR-015**：系统必须记录订单定位、方案生成、风险判断、客户确认、内部决定、业务执行、结果核验、客户通知和问题状态变化。
- **FR-016**：系统必须生成结构化处理摘要；摘要生成失败不得改变已经核验的业务结果，但必须留下失败记录并导致本次 Demo 验收失败。
- **FR-017**：客户可见信息、内部业务信息和独立核验所需信息必须按最小必要原则隔离，任何角色不得读取超出当前职责和当前问题范围的数据。
- **FR-018**：所有演示、测试和参赛证据必须使用合成数据，不得使用真实客户、订单、邮件、内部代码或未公开业务规则。

### Key Entities

- **Service Case**：代表一次客户问题及其生命周期，关联客户、目标订单、当前处理结果和历史记录。
- **Customer Identity**：代表进入服务前已经确认的客户身份，用于限定可访问的订单范围。
- **Order**：代表客户名下的酒店预订，包含酒店、入住日期、订单状态和确认信息。
- **Supplier Exception**：代表影响目标订单履约的结构化供应异常事实。
- **Resolution Proposal**：代表向客户或内部运营人员展示的处理方案及其版本、价差和预期结果。
- **Risk Decision**：代表根据有效业务规则得到的风险结论、原因和所需控制。
- **Confirmation / Approval**：代表客户确认或内部运营决定，并与具体问题和方案版本绑定。
- **Execution Outcome**：代表订单是否发生实际变更及其结果。
- **Verification Outcome**：代表实际订单结果与确认方案之间的比较结论和差异。
- **Audit Record**：代表本次服务中关键输入、决定、动作、结果和时间信息的可复核记录。
- **Case Summary**：代表问题、证据、方案、执行和核验结果的结构化摘要；V0.1 不要求历史摘要召回。

## Success Criteria

### Measurable Outcomes

- **SC-001**：Golden Journey 能从客户首次报障运行到已解决，内部客服和运营人员介入次数为 0。
- **SC-002**：初始信息不足时，系统能主动索取缺失字段，并在客户补充后唯一定位 `C001` 的目标订单。
- **SC-003**：针对 `C001` 的全部对话、处理结果和审计记录中，`C002` 订单信息暴露次数为 0。
- **SC-004**：系统能基于结构化异常事实生成包含替代酒店、入住日期和 180 元价差的处理方案。
- **SC-005**：客户确认前订单变更次数为 0；确认后目标订单只发生 1 次符合方案的变更。
- **SC-006**：实际订单未更新的异常样例中，系统判定成功的次数为 0，问题不得被标记为已解决。
- **SC-007**：800 元价差样例在没有内部审批时，订单变更次数为 0；运营人员能够对当前方案完成一次 `APPROVE` 或 `REJECT`。
- **SC-008**：补充信息请求发出后 24 小时无有效回复时，问题被标记为未完成；关闭后回复恢复原问题，新增重复问题数量为 0。
- **SC-009**：Golden Journey 中订单定位、风险判断、确认、执行、核验、通知和问题状态变化七类关键行为的记录完整率为 100%。
- **SC-010**：Golden Journey 结束后生成字段完整的结构化处理摘要；摘要生成失败时本次 Demo 验收结果为失败。

## Assumptions

- 客户在进入服务前已经通过现有登录系统完成身份确认；V0.1 不建设验证码、匿名身份匹配或完整 IAM。
- 供应异常、替代酒店、订单和业务规则均以预置的结构化合成数据提供，不解析真实供应商邮件。
- Golden Journey 中目标替代酒店价差为 180 元，现行业务规则要求客户确认后可以自动改订；800 元价差样例用于验证内部审批边界。
- 客户补充信息、选择或确认方案属于正常客户服务交互，不计为内部人工介入；内部客服或运营人员参与调查、决定、审批或执行才计为内部人工介入。
- V0.1 只覆盖酒店供应异常改订，不覆盖退款、取消、航班变更、多渠道聚合、知识召回或生产系统接入。
- GOAI Agent Infra 赛道要求方案以 AgentTeams 为多 Agent 协同基点，至少包含 3 个不同职能 Agent，并把 Skill 作为必选能力；具体 Agent、Room、Skill、MCP、状态机和技术映射在本 Spec 确认后进入 Plan 体系。
- V0.1 只验证高风险方案被阻断并产生 `APPROVE / REJECT` 决定，不要求完成高风险方案批准后的端到端执行。
- 所有执行均针对本地合成业务系统；外部报名、作品提交、群聊加入或消息发送不在本 Feature 的授权范围内。
