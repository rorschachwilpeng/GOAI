# GOAI 多 Agent 协作表

最后更新：2026-08-14

## 1. 文档目的

本文件约束建设 GOAI 项目的长期 Codex Agent：谁负责规划，谁负责实施，什么情况下必须停下来同步，以及怎样用证据验收。

本项目只保留两个长期项目 Agent，避免为了分工增加沟通成本。临时子 Agent 只执行一次性任务，不登记为长期角色。

## 2. 事实源优先级

出现冲突时按以下顺序处理：

1. 用户在当前对话中的最新明确决定；
2. `AGENTS.md` 与本文件规定的项目治理和授权边界；
3. 用户确认的 `specs/*/spec.md`，用于定义要构建什么、边界和验收标准；
4. Spec 确认后派生的 `plan.md` 和 `tasks.md`，分别定义实现方案与执行任务；
5. 代码、配置、测试、Trace 和运行记录，用于判断能力是否真实完成；
6. Agent 的分析、历史讨论和默认假设。

截至 2026-08-14，功能 `001` 的 Spec 与 Plan 已确认，`tasks.md` 已生成。Project Room、角色级 MCP 权限等能力在对应任务验收前仍属于方案设计，不得提前写成已实现事实。

## 3. 两类 Agent 不得混淆

| 类型 | 成员 | 服务对象 | 运行位置 | 事实源 |
| --- | --- | --- | --- | --- |
| 建设项目的 Codex Agent | Planning Agent、执行 Agent | GOAI 项目建设与参赛交付 | Codex 长期任务 | 本文件、Spec、后续 Plan 与 Tasks |
| 参赛产品内部 Agent | Frontline Agent、Resolution Agent、Manager Agent、Verification Agent | 酒店供应异常的自主客服闭环 | AgentTeams 与对应 Room | 产品 Spec、AgentTeams 配置、运行证据 |

项目 Agent 负责把产品做出来；产品 Agent 是被设计、实现和验证的系统角色。项目 Agent 不得把自己的工作分工写进产品架构，也不得把产品 Agent 当作 Codex 项目成员调度。

## 5. 分工与授权边界

| 角色 | 结果责任 | 可自主处理 | 不可自主决定 | 主写入范围 | 成功标准 |
| --- | --- | --- | --- | --- | --- |
| Planning Agent | Spec、优先级、架构决策、实施计划、验收和跨任务风险一致 | 维护 Spec；在 Spec 确认后派生 Plan 与 Tasks；分配任务；核对证据；组织用户决策 | 替用户提交作品或对外发送消息；在没有证据时宣布能力已实现；包揽全部日常实现 | `specs/`、`01-项目背景/`、`03-需求定义/`、`04-方案设计/`，以及任务与验收记录 | 产品边界清楚；每项实施可追溯到验收标准；实现状态与证据一致 |
| 执行 Agent | 按已确认任务完成 AgentTeams、Skills、MCP/Mock、测试、运行证据和参赛素材 | 在任务允许范围内实现、调试、测试、取证；提出技术取舍；更新任务状态和证据位置 | 自行改变产品范围、角色职责、架构和验收口径；把模拟或设计写成已实现；绕过用户授权执行外部行动 | `workspace/`、`06-评估验证/`、`07-参赛材料/`、`08-交付输出/`；只按任务要求更新状态和证据 | 交付物可运行或可检查；验收项有测试、Trace、截图或运行记录；遗留风险明确 |

## 6. 工作流

```text
用户确认 Spec
    ↓
Planning Agent 编写 Plan
    ↓
Planning Agent 从 Spec 与 Plan 派生 Tasks
    ↓
执行 Agent 按 Tasks 实施和验证
    ↓
执行 Agent 提交证据并“请验收”
    ↓
Planning Agent 对照 Spec 验收
    ↓
用户确认关键结果或进入下一阶段
```

规则：

- 需求变化先改 Spec，再同步 Plan、Tasks、测试和演示材料。
- 执行 Agent 可以提出变更建议，但不能先实现再倒逼 Spec 接受。
- 每项正式任务只有一个主责任 Agent。
- “已完成”表示交付物和证据都齐备；只有代码或文字说明不算完成。

## 7. 任务与状态

### 7.1 任务编号

- Planning Agent：`GOAI-PLAN-*`
- 执行 Agent：`GOAI-EXEC-*`

### 7.2 标准任务字段

| 字段 | 定义 |
| --- | --- |
| 任务 ID | 使用上述编号，保持唯一 |
| 主责 Agent | 唯一对结果负责的长期项目 Agent |
| 目标 | 本任务必须解决的问题 |
| 事实来源 | 必须读取的 Spec、文件、数据或用户决定 |
| 允许写入范围 | 可以修改的目录和文件 |
| 输出与验收标准 | 可检查的交付物和通过条件 |
| 证据位置 | 测试结果、Trace、截图、视频或运行记录路径 |
| 依赖与期限 | 前置输入、阻塞和外部时间点 |
| 汇报类型 | 无、请决策、请协调、请升级或请验收 |
| 状态 | 待分配、进行中、待用户确认、被阻塞、请验收、已完成或已归档 |

任务进入 `请验收` 后，由 Planning Agent 核对证据。验收通过才改为 `已完成`；退回时恢复为 `进行中`，并写明未满足的验收项。

## 8. 四类向上汇报

| 类型 | 触发事实 | Planning Agent 动作 |
| --- | --- | --- |
| `请决策` | 存在互斥方案；选择会改变 Spec、范围、架构、角色边界或验收口径；必须由用户确认才能继续 | 给出选项、影响和推荐，组织用户确认并记录决定 |
| `请协调` | 需要另一 Agent 提供输入、接收交付，或同步修改 Plan、Tasks 和上下游材料 | 指定主责、交付物、顺序与验收标准 |
| `请升级` | 没有替代路径的阻塞；截止时间受威胁；发现安全、隐私、凭据、授权或真实性风险；既有交付因重大错误失效 | 先控制风险，再调整优先级、范围或实现路径 |
| `请验收` | 任务约定的交付物、测试和证据已经齐备 | 对照 Spec 与任务标准，决定通过或退回 |

每次汇报必须包含：汇报类型、任务 ID、触发事实、证据位置、影响范围、需要 Planning Agent 采取的动作。普通进展和没有行动要求的局部结果不即时上报。

如果用户直接要求执行 Agent 改变产品定义：

- 用户已经明确作出单一决定时，使用 `请协调`，由 Planning Agent 先同步 Spec、Plan 和 Tasks；
- 输入仍有互斥解释时，使用 `请决策`；
- 在正式事实源同步完成前，执行 Agent 不实施受影响部分。

## 9. 交接、验收与证据

跨 Agent 交接至少写明：任务 ID、发送与接收 Agent、当前结论、文件或证据位置、请求动作、验收标准、依赖和期限。

执行 Agent 提交验收时必须说明：

1. 修改了什么；
2. 对应 Spec 的哪项要求；
3. 如何验证，结果是什么；
4. 证据保存在哪里；
5. 还有哪些未实现、模拟执行或已知风险。

Planning Agent 只按证据验收。材料中的能力状态统一使用：`已实现`、`模拟执行`、`方案设计`、`后续规划`。

## 11. Agent Onboarding

长期项目 Agent 接收正式任务前必须读取：

1. 根目录 `AGENTS.md`；
2. 本文件；
3. `specs/README.md` 与当前功能的 `spec.md`；
4. 与任务直接相关的项目材料和 `workspace/README.md`；
5. 正式 `plan.md`、`tasks.md`（仅在它们已经创建后）。

读完后需核对自己的结果责任、不可自主决定事项、允许写入范围、验收标准和当前任务状态。治理规则更新后重新读取即可，不要求重复发送形式化确认。

## 12. 数据与外部行动边界

- 只使用合成数据和公开资料，不使用 PKFARE 内部代码、真实邮件、订单、客户信息、商业秘密或未公开规则。
- API Key、Token、Cookie 和其他凭据不得写入项目文件、日志、截图或参赛材料；发现暴露风险立即 `请升级`。
- 未经用户逐次明确授权，不报名、不提交作品、不加入群聊、不发送外部消息，也不声称已经完成这些动作。
- 对外材料必须区分真实运行、Mock 执行、方案设计和后续规划。
